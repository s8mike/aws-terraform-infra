# Database Schema

The application uses PostgreSQL through SQLAlchemy. The schema is designed to measure operator performance in context, not just by raw task duration. Task logs, delay logs, and working conditions are stored separately so manager dashboards can distinguish productive time from uncontrollable operational delays.

## Tables

### users

Stores login identity and role information.

Columns:

- `id`
- `email`
- `full_name`
- `password_hash`
- `role`
- `is_active`
- `created_at`
- `updated_at`

Roles:

- `operator`
- `manager`
- `admin`

### operator_profiles

Stores operator-specific information linked one-to-one with `users`.

Columns:

- `id`
- `user_id`
- `employee_number`
- `certification_level`
- `default_crane_id`
- `created_at`
- `updated_at`

### manager_profiles

Stores manager-specific information linked one-to-one with `users`.

Columns:

- `id`
- `user_id`
- `department`
- `phone_number`
- `created_at`
- `updated_at`

### admin_profiles

Stores admin-specific information linked one-to-one with `users`.

Columns:

- `id`
- `user_id`
- `department`
- `created_at`
- `updated_at`

### cranes

Stores mobile harbour crane assets.

Columns:

- `id`
- `code`
- `mhc_number`
- `name`
- `manufacturer`
- `model`
- `capacity_tonnes`
- `location`
- `is_active`
- `created_at`
- `updated_at`

### reference_data

Stores administrator-managed options for operator forms and reports. A unique
`category` plus `code` prevents duplicate values while `is_active` retires an
option without changing historical task or delay records.

Columns:

- `id`
- `category` such as `nature_of_work`, `working_area`, `delay_type`, or `shift_code`
- `code`
- `label`
- `short_key` for concise operational delay labels such as `AT`
- `description`
- `is_active`
- `created_at`
- `updated_at`

### shifts

Stores each operator work period on a crane.

Columns:

- `id`
- `operator_id`
- `crane_id`
- `mhc_number`
- `shift_code`
- `started_at`
- `ended_at`
- `status`
- `notes`
- `created_at`
- `updated_at`

Common statuses:

- `active`
- `completed`
- `cancelled`

Shift code values:

- `A`
- `B`
- `C`

Lifecycle note:

- `ended_at` is nullable in the database because active shifts are open while work is happening.
- The Phase 4 end-shift endpoint requires `ended_at` before a shift can move to `completed`.

### task_logs

Stores operational work records for loading, discharging, tight-space work, and other crane activities.

Columns:

- `id`
- `shift_id`
- `operator_id`
- `crane_id`
- `nature_of_work`
- `working_area`
- `vessel_name`
- `bay_reference`
- `container_count`
- `started_at`
- `ended_at`
- `status`
- `notes`
- `created_at`
- `updated_at`

Lifecycle note:

- `ended_at` is nullable in the database because active task logs are open while work is happening.
- The Phase 4 end-task endpoint requires `ended_at` before a task can move to `completed`.

### delay_logs

Stores operational delays attached to a task log.

Columns:

- `id`
- `task_log_id`
- `delay_type`
- `custom_delay_type`
- `started_at`
- `ended_at`
- `duration_minutes`
- `is_operator_controllable`
- `notes`
- `created_at`
- `updated_at`

Lifecycle note:

- `ended_at` is nullable in the database because active delays are open while downtime is happening.
- The Phase 4 end-delay endpoint requires `ended_at` before a delay can close.

### working_conditions

Stores environmental and operational context for a shift.

Columns:

- `id`
- `shift_id`
- `weather_condition`
- `visibility`
- `wind_condition`
- `deck_condition`
- `congestion_level`
- `notes`

- `created_at`
- `updated_at`

- `operator_id`

- `snapshot_type`
- `calculated_at`
- `created_at`
- `updated_at`

Snapshot types:

- `shift`
- `task`
- `daily`

### report_exports

Stores report export requests and generated file metadata.

Columns:

- `id`
- `requested_by_id`
- `report_type`
- `file_format`
- `date_from`
- `date_to`
- `status`

- `created_at`

### audit_logs

Stores important user and system actions for traceability.

Columns:

- `id`
- `actor_id`
- `action`
- `entity_type`
- `entity_id`
- `description`
- `created_at`

## Relationships

- One `user` may have one `operator_profile`, `manager_profile`, or `admin_profile`.
- One `crane` may have many `shifts`.
- One `shift` belongs to one operator user and one crane.
- One `shift` may have many `task_logs`.
- One `shift` may have many `working_conditions`.
- One `task_log` may have many `delay_logs`.
- One `shift` may have many `performance_snapshots`.
- One `task_log` may have many task-level `performance_snapshots`.
- One manager or admin user may request many `report_exports`.
- One user may produce many `audit_logs`.
- Each managed `reference_data` entry is independent and retains historical meaning when deactivated.

## Domain Reference Values

Reference values are stored as strings in the first implementation. This keeps the schema simple and allows the admin workflow to later manage reference data without PostgreSQL enum migrations.

### Nature Of Work

- `across_heights_portside`
- `deck_free_bay`
- `underdeck_free_bay`
- `underdeck_across_heights`
- `loading_export_free_bay`
- `loading_export_across_heights`
- `loading_empty_single`
- `loading_empty_twin`
- `discharge_oog`
- `tight_space_cranes`

### Working Areas

- `port_side`
- `deck`
- `underdeck`
- `tight_space`
- `other`

### Delay Types

- `awaiting_containers_empty`
- `awaiting_containers_export`
- `awaiting_trucks`
- `awaiting_clerks`
- `awaiting_stevedores`
- `control_room_modification`
- `wrong_instructions`
- `breakdown`
- `rainfall`
- `vessel_command_instructions`
- `crane_travelling`
- `other_delay`

Initial delay short keys include `AConE` (awaiting empty containers), `AConX`
(awaiting export containers), `AT` (awaiting trucks), `AClerks`, `AStev`, and
`CT` (crane travelling). Admins may maintain these values through the Phase 6
reference-data endpoints.

`custom_delay_type` is available when the delay is known locally but has not yet been added to the standard dropdown. This lets the team capture real port conditions immediately, then later decide whether to promote that value into managed reference data.

## Performance Calculation Direction

The reporting phase will calculate:

- total task minutes
- total delay minutes
- effective work minutes
- container count
- moves per hour
- delay minutes by delay type
- operator comparison by crane, shift, date range, work type, and vessel
