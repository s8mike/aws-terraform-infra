# Local Development Guide (Backend)

This guide takes you from an empty machine to a working local copy of the Mecandjeo MHC Monitoring API, running in Docker with PostgreSQL. Every step shows the command and what you should see afterwards. You do not need earlier Docker, FastAPI or pytest experience.

The web app (React) has its own guide: `docs/PROJECT-PHASES/Phase-10.1-Frontend-Development.md`. A map of the frontend files is in `docs/7. Frontend-Structure.md`.

Other guides: `docs/PROJECT-PHASES/Phase-10.2-Database-Migrations-Explained.md` (schema changes), `docs/PROJECT-PHASES/Phase-11.6-TESTING-GUIDE.md` (all test levels), `docs/PROJECT-PHASES/Phase-11.4-PLAYWRIGHT-GUIDE.md` (browser tests), `docs/PROJECT-PHASES/Phase-11.1-CONTAINER-SECURITY.md` (non-root containers and scanning), `docs/PROJECT-PHASES/Phase-11.2-DEPENDENCY-LOCKING.md` (locked packages and how to update them), `docs/PROJECT-PHASES/Phase-11.5-SCRIPTS-REFERENCE.md` (every script, with its command and expected output) and `docs/PROJECT-PHASES/Phase-11.3-DEVOPS-CONCEPTS-MAP.md` (the DevOps ideas used in this project).

Commands are for **Git Bash** (the terminal that comes with Git for Windows). A PowerShell appendix is at the end. Lines starting with `#` are comments, so you can paste them along with the commands.

## 1. What you will have at the end

- Four containers started by one command: `crane-db` (PostgreSQL), `crane-migrate` (a one-off job that creates the tables), `crane-app` (the API) and `crane-web` (nginx serving the web app).
- All database tables created by migrations (the `crane-migrate` job runs `alembic upgrade head`).
- 28 standard reference values: 5 work types, 8 working areas, 12 delay types and 3 shift codes.
- 3 sample cranes (`MHC-01`, `MHC-02`, `MHC-03`).
- One admin account created from your own settings.
- Optional demo data: `operator1`, `operator2` and `manager1`, with sample shifts, tasks and delays.
- Interactive API documentation at `http://localhost:8004/docs`.
- The web app at `http://localhost:8080`.
- 71 automated backend tests passing, and a one-command stack check (`bash scripts/verify_stack.sh`).

## 4. Create your local settings file (`.env.docker`)

The application reads its settings from a file called `.env.docker`. It holds secrets, so it is **not** stored in Git. You create it from the example file.

**Step 4.1. Copy the example**

```bash
cp .env.docker.example .env.docker
```

**Step 4.2. Generate a secret key.** The key signs login tokens and must be at least 32 characters:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Copy the long string it prints.

**Step 4.3. Edit the file** in any editor (for example `notepad .env.docker`) and set these values:

```dotenv
SECRET_KEY=<paste the generated key here>

BOOTSTRAP_ADMIN_EMAIL=admin@example.com
BOOTSTRAP_ADMIN_PASSWORD=<a local-only password, 12 or more characters>
SEED_SAMPLE_DATA=true
```

**Rules for these values:**

- Use `admin@example.com` or another real-looking address. Do **not** use a `.test`, `.local` or `.invalid` domain: the email check rejects them and login fails.
- Make the password at least 12 characters. A shorter one stops the application with `BOOTSTRAP_ADMIN_PASSWORD must be at least 12 characters`.
- Do not put spaces, quotes, `#` or `$` in the password. Docker Compose treats `$` as a variable and `#` can start a comment, so either would silently change the password.
- Never commit `.env.docker`. Confirm it is ignored:

```bash
git check-ignore .env.docker
```

It should print `.env.docker`. If it prints nothing, add `.env.docker` to `.gitignore` before continuing.

## 5. Build and start the application

```bash
docker compose --env-file .env.docker up -d --build --wait
```

What the flags mean:

- `--env-file .env.docker` tells Compose where your settings are.
- `up` creates and starts the containers.
- `-d` runs them in the background.
- `--build` rebuilds the images from your current code.
- `--wait` makes the command **wait until every service is healthy** before it returns, or fail if one does not become healthy. It replaces guessing with `sleep`.

Four containers start, in this order:

| Container | What it is | Normal state afterwards |
|---|---|---|
| `crane-db` | PostgreSQL 17 | Up, healthy |
| `crane-migrate` | A one-off job that runs `alembic upgrade head` to create or update the tables | **Exited (0)**: it is meant to finish |
| `crane-app` | The API (FastAPI) | Up, healthy |
| `crane-web` | nginx serving the web app and forwarding `/api` to the API | Up, healthy |

The first build downloads the Python, Node, nginx and PostgreSQL images and installs the packages, so it can take several minutes. Later builds are much faster because Docker reuses unchanged layers. The command ends with one line per container; `crane-migrate` shows as `Exited`, which is correct.

## 6. Check that it is healthy

**6.1. One-command check (recommended)**

```bash
bash scripts/verify_stack.sh
```

It checks the containers, the web server, the API, the migrations, the security settings, the locked packages and a real login. It ends with:

```text
Result: 14 passed, 0 failed
```

If a check fails, its line is followed by a "what to try" hint. Every check is explained in `docs/PROJECT-PHASES/Phase-11.5-SCRIPTS-REFERENCE.md`. The manual checks below show what the script does under the hood.

**6.2. Container status**

```bash
docker compose --env-file .env.docker ps -a
```

`crane-db`, `crane-app` and `crane-web` should say `(healthy)`. `crane-migrate` should say `Exited (0)`. The `-a` matters: without it the finished migration job is hidden.

**6.3. Health endpoints**

```bash
curl http://localhost:8004/health
curl http://localhost:8080/health
curl -s -w "\n%{http_code}\n" http://localhost:8080/healthz | tail -n 1
```

Expected: `{"status":"ok"}` for the first two (the second goes through the web server's proxy) and `200` for the third, which nginx answers by itself.

**6.4. The web app**

Open `http://localhost:8080` in a browser. You should see the login page.

**6.5. The startup (bootstrap) log**

```bash
docker compose --env-file .env.docker logs crane-app | grep "bootstrap:"
```

On the first start on an empty database:

```text
bootstrap: reference_data_added=28 cranes_added=3 admin_created=True
```

On every later start it shows zeros and `False`, because the data already exists:

```text
bootstrap: reference_data_added=0 cranes_added=0 admin_created=False
```

The zeros are correct. They prove that restarting never duplicates data or overwrites your admin password.

## 7. Log in and get an access token

Most endpoints need a token. This block reads the admin email and password from your `.env.docker` (nothing to type), logs in, and keeps the token in a shell variable. Paste it as one block:

```bash
ADMIN_EMAIL=$(grep -E '^BOOTSTRAP_ADMIN_EMAIL=' .env.docker \
  | cut -d= -f2- | tr -d '\r')
ADMIN_PASSWORD=$(grep -E '^BOOTSTRAP_ADMIN_PASSWORD=' .env.docker \
  | cut -d= -f2- | tr -d '\r')

LOGIN_RESPONSE=$(curl -s -X POST http://localhost:8004/api/auth/login \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"$ADMIN_EMAIL\",\"password\":\"$ADMIN_PASSWORD\"}")

TOKEN=$(echo "$LOGIN_RESPONSE" \
  | sed -E 's/.*"access_token":"([^"]+)".*/\1/')
unset ADMIN_PASSWORD
echo "token length: ${#TOKEN}"
```

Expected: a token length of roughly 170 to 180. If the number is large (the length of the whole response), login failed: run `echo "$LOGIN_RESPONSE"` to see the message. `Invalid email or password` means the email or password in `.env.docker` is not the one the admin was created with.

The `TOKEN` variable exists only in this terminal window. Tokens expire after `JWT_EXPIRE_HOURS` (24 by default).

**Using the token in Swagger (browser):**

1. Open `http://localhost:8004/docs`.
2. Click **Authorize** (top right).
3. Paste the token alone, without the word `Bearer`.
4. Click **Authorize**, then **Close**.

Every request you try on that page now sends your token.

## 8. Check the lookup values and sample cranes

`GET /api/lookups` returns the values operators choose from. Any logged-in user can read it.

```bash
LOOKUPS=$(curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8004/api/lookups)
echo "mhc numbers: $(echo "$LOOKUPS" | grep -o '"mhc_number"' | wc -l)"
echo "total codes: $(echo "$LOOKUPS" | grep -o '"code"' | wc -l)"
```

Expected: `mhc numbers: 3` and `total codes: 28` (5 + 8 + 12 + 3).

Confirm the endpoint rejects callers who are not logged in:

```bash
curl -s -w "\n%{http_code}\n" http://localhost:8004/api/lookups | tail -n 1
```

Expected: `401`.

The pattern `curl -s -w "\n%{http_code}\n" ... | tail -n 1` prints only the status code. Do not use `curl -o /dev/null` for this: in Git Bash on Windows it can fail with exit code 23 even when the request worked.

| Message | Fix |
|---|---|

| `Stopped at line N: ...` | Copy that line when asking for help |

### 9.2 Try a workflow by hand

This signs in as the demo operator, starts a shift on the unused `MHC-03`, and shows that invalid work types are refused. It uses the variables from section 7 only for the admin, so it logs in again as the operator.

```bash
BASE=http://localhost:8004
JSON="Content-Type: application/json"

OP_TOKEN=$(curl -s -X POST $BASE/api/auth/login -H "$JSON" \
  -d '{"email":"operator1@example.com","password":"Securepass123!"}' \
  | sed -E 's/.*"access_token":"([^"]+)".*/\1/')
echo "operator token length: ${#OP_TOKEN}"

SHIFT_ID=$(curl -s -X POST $BASE/api/shifts/start -H "$JSON" \
  -H "Authorization: Bearer $OP_TOKEN" \
  -d '{"mhc_number":"MHC-03","shift_code":"C",
       "started_at":"2026-10-08T06:00:00"}' \
  | sed -E 's/.*"id":([0-9]+).*/\1/')
echo "shift id: $SHIFT_ID"
```

Expected: a token length near 176 and a shift id. Now try an invalid and then a valid work type:

```bash
curl -s -w "\n%{http_code}\n" -X POST $BASE/api/task-logs/start \
  -H "$JSON" -H "Authorization: Bearer $OP_TOKEN" \
  -d "{\"shift_id\":$SHIFT_ID,
       \"nature_of_work\":\"not_a_real_type\",
       \"working_area\":\"deck_free_bay\",
       \"started_at\":\"2026-10-08T06:10:00\"}" \
  | tail -n 1

curl -s -w "\n%{http_code}\n" -X POST $BASE/api/task-logs/start \
  -H "$JSON" -H "Authorization: Bearer $OP_TOKEN" \
  -d "{\"shift_id\":$SHIFT_ID,
       \"nature_of_work\":\"discharging\",
       \"working_area\":\"deck_free_bay\",
       \"started_at\":\"2026-10-08T06:10:00\"}" \
  | tail -n 1
```

Expected: `400` for the invalid type, then `201` for the valid one. This leaves `operator1` with an open shift and task, which you can end from the operator screen of the web app.

Why this matters: operators may only choose values an admin has approved. That keeps manager reports consistent, because `deck_free_bay` and `Deck free bay` can never become two categories.

## 10. Run the automated tests

The backend tests run on your machine (not in Docker) against a temporary SQLite database, so they never touch your PostgreSQL data.

**10.1. Create a Python environment (first time only)**

```bash
python -m venv .venv
source .venv/Scripts/activate
pip install -r requirements-dev.txt
```

Your prompt starts with the environment name, for example `(.venv)`. `requirements-dev.txt` installs the exact locked package versions that the container uses (its first line is `-r requirements.lock`, where `-r` means "also read the packages listed in that file") plus the test-only tools `pytest` and `httpx`. The container image does not contain the test tools.

**10.2. Run everything**

```bash
python -m pytest tests -q
```

Expected last line:

```text
71 passed, 1 warning
```

It takes about a minute. The one warning is a harmless notice from a library (`httpx`).

**10.3. Useful variations**

```bash
# one line per test
python -m pytest tests -v
# one file
python -m pytest tests/test_lookups.py -v
# tests with "password" in the name
python -m pytest tests -k "password" -v
# stop at the first failure
python -m pytest tests -x
```

In a new Git Bash window, run `source .venv/Scripts/activate` again before testing. The frontend tests (107) are run with `npm run test` from the `frontend` folder; see `docs/PROJECT-PHASES/Phase-10.1-Frontend-Development.md`. The browser tests (6) run from the `e2e` folder; see `docs/PROJECT-PHASES/Phase-11.4-PLAYWRIGHT-GUIDE.md`. All three levels are compared in `docs/PROJECT-PHASES/Phase-11.6-TESTING-GUIDE.md`.

## 11. Understanding the tests

### 11.1 What an automated test is

A test is a small program that uses your application the way a person would, then checks the result with `assert`. If every `assert` is true the test passes; if one is false the test fails and shows which line. Tests tell you within seconds whether a change broke something.

| Word | Meaning |
|---|---|
| `assert x == y` | Fails the test unless `x` equals `y` |
| fixture | Setup code pytest runs for a test (for example "a fresh database") |
| `client` | A fake browser that calls the API without starting a server |
| `monkeypatch` | Temporarily changes a setting for one test, then restores it |
| `parametrize` | Runs one test several times with different inputs |
| `pytestmark` | A line at the top of a file that applies a fixture to every test in it |
| status code | `200` OK, `201` created, `204` done with no body, `400` bad input, `401` not signed in, `403` not allowed, `404` not found, `409` conflict, `422` invalid fields |

### 11.2 How the test environment works (`tests/conftest.py`)

1. It points the app at a temporary SQLite file (`tests/test_app.db`) by setting `DATABASE_URL`, `SECRET_KEY` and `JWT_EXPIRE_HOURS` **before** the app is imported. The app refuses to import without `DATABASE_URL`, so no `app` import may appear above those lines.
2. The `reset_database` fixture runs before every test: it drops and recreates all tables, so tests cannot affect each other.
3. The `seeded_reference_data` fixture loads the 28 standard reference values. Only tests that need it ask for it.
4. The `client` fixture gives each test the fake browser.
5. `pytest_sessionfinish` deletes the temporary database when all tests finish.

### 11.4 Tests added in Phase 11 (10 tests)

#### 1. `tests/test_migrations.py` (6 tests)

These tests run the migration history in `migrations/` against throwaway SQLite files, so your real database is never touched.

1. **`test_migrations_build_the_schema_the_models_describe`**
   - **What it proves:** Running every migration creates all 13 tables, and `alembic check` finds no difference from the models.

2. **`test_downgrade_removes_every_table`**
   - **What it proves:** The migration can be undone completely.

3. **`test_upgrade_is_safe_to_repeat`**
   - **What it proves:** Running `upgrade head` twice changes nothing (the migrate job runs on every start).

4. **`test_history_has_a_single_head`**
   - **What it proves:** The history is one straight line with exactly one latest revision (`0001`).

5. **`test_stamp_adopts_an_existing_database_without_changing_it`**
   - **What it proves:** A database built the old way can be adopted with `alembic stamp head` and keeps its data.

6. **`test_upgrade_refuses_an_unstamped_existing_database`**
   - **What it proves:** Upgrading a database that has tables but was never stamped fails loudly ("already exists") instead of corrupting it.

#### 2. `tests/test_lifespan.py` (4 tests)

These tests check what the API does at start-up under its two settings, using stand-in functions so nothing real is created.

1. **`test_start_up_does_nothing_when_both_settings_are_off`**
   - **What it proves:** `AUTO_CREATE_SCHEMA=false` and `RUN_BOOTSTRAP=false` start nothing (the production setting).

2. **`test_bootstrap_alone_does_not_create_tables`**
   - **What it proves:** The bootstrap can run on a schema built by migrations.

3. **`test_create_tables_alone_does_not_run_bootstrap`**
   - **What it proves:** The two settings are independent.

4. **`test_tables_are_created_before_the_bootstrap_runs`**
   - **What it proves:** With both on, the tables come first.

## 13. Settings reference

These settings live in `.env.docker` (see `.env.docker.example`).

1. **`APP_PORT`**
   - **Purpose:** Port on your machine.
   - **Local value:** `8004`.

2. **`DATABASE_URL`**
   - **Purpose:** Defines how the API reaches PostgreSQL.
   - **Local value:** Uses the `crane-db` service name.

3. **`SECRET_KEY`**
   - **Purpose:** Signs login tokens (32+ characters).
   - **Local value:** Generated random string.

4. **`JWT_EXPIRE_HOURS`**
   - **Purpose:** Defines the token lifetime.
   - **Local value:** `24`.

5. **`AUTO_CREATE_SCHEMA`**
   - **Purpose:** Lets the API create the tables itself at start-up (the old way).
   - **Local value:** `false` — the tables come from migrations.

6. **`RUN_BOOTSTRAP`**
   - **Purpose:** Adds reference data, sample cranes, and the first admin at start-up (safe to repeat).
   - **Local value:** `true`.

7. **`BOOTSTRAP_ADMIN_EMAIL`**
   - **Purpose:** Email address of the first admin.
   - **Local value:** `admin@example.com`.

8. **`BOOTSTRAP_ADMIN_PASSWORD`**
   - **Purpose:** Password of the first admin (12+ characters).
   - **Local value:** Your own choice.

9. **`SEED_SAMPLE_DATA`**
   - **Purpose:** Creates 3 sample cranes.
   - **Local value:** `true` locally only.

10. **`POSTGRES_*`**
    - **Purpose:** Defines the database name, user, password, and image version.
    - **Local value:** See the example file.

11. **`WEB_PORT`**
    - **Purpose:** Port of the web app on your machine.
    - **Local value:** `8080`.

### Important configuration rules

- `SEED_SAMPLE_DATA` is for local development only. Do not enable it in a cloud environment.
- Keep `AUTO_CREATE_SCHEMA=false` everywhere. Tables and subsequent changes must come from migrations (see `docs/PROJECT-PHASES/Phase-10.2-Database-Migrations-Explained.md`).
- `RUN_BOOTSTRAP=true` is safe everywhere because it never duplicates data.

## 14. Troubleshooting

1. **Startup log says `admin_created=False` on the first run**
   - **Cause:** `BOOTSTRAP_ADMIN_*` is missing from the real `.env.docker`.
   - **Fix:** Add them, then run `up -d --force-recreate crane-app`.

2. **Container keeps restarting; log mentions `at least 12 characters`**
   - **Cause:** The bootstrap password is too short.
   - **Fix:** Use 12+ characters, then force-recreate.

3. **Login fails for `admin@example.test`**
   - **Cause:** `.test` is a reserved domain the email check refuses.
   - **Fix:** Use `admin@example.com`.

4. **The `.env.docker` password works nowhere**
   - **Cause:** `$`, `#`, quotes, or spaces were altered by Compose.
   - **Fix:** Choose a password without them; reset with `down -v` if the admin already exists.

5. **You edited `.env.docker` and nothing changed**
   - **Cause:** `restart` does not re-read the file.
   - **Fix:** Run `up -d --force-recreate crane-app`.

6. **The bootstrap log line is missing right after start**
   - **Cause:** Output was buffered (fixed in current code).
   - **Fix:** Run `up -d --build`.

7. **`failed to solve ... no such host` while building**
   - **Cause:** Docker cannot resolve DNS to download the base image.
   - **Fix:**
     - Check your internet connection.
     - Quit and reopen Docker Desktop.
     - If the problem persists, add `"dns": ["8.8.8.8", "1.1.1.1"]` in **Settings > Docker Engine**, then click **Apply & restart**.

8. **`curl ... -o /dev/null` fails (`exit 23`, or a script stops)**
   - **Cause:** Windows curl cannot write to `/dev/null`.
   - **Fix:** Use:
     ```bash
     curl -s -w "\n%{http_code}\n" ... | tail -n 1
     ```

9. **"Invalid email or password" for `operator1`**
   - **Cause:** The database was reset and the demo data was not reloaded.
   - **Fix:**
     ```bash
     bash scripts/seed_demo_data.sh
     ```

10. **Old work types still appear after a taxonomy update**
    - **Cause:** Old values were never retired in your database.
    - **Fix:** Retire them in the admin screen, or reset with `down -v`.

11. **`ImportError ... DATABASE_URL environment variable is required` in tests**
    - **Cause:** An `app` import sits above the `os.environ[...]` lines in `tests/conftest.py`.
    - **Fix:** Move it below them.

12. **`NameError: name 'pytest' is not defined` in a test file**
    - **Cause:** The file uses `pytest.mark...` without importing it.
    - **Fix:** Add `import pytest` at the top.

13. **`ModuleNotFoundError: No module named 'pytest'`**
    - **Cause:** Dependencies are not installed in the active environment.
    - **Fix:** Activate the virtual environment and install the development requirements:
      ```bash
      source .venv/Scripts/activate
      pip install -r requirements-dev.txt
      ```
      Use `requirements-dev.txt`, which includes `pytest` and `httpx`.

14. **Swagger Authorize shows a username and password form**
    - **Cause:** The container runs an old image.
    - **Fix:** Run `up -d --build`, then hard refresh with `Ctrl+Shift+R`.

15. **`401` on a request that worked earlier**
    - **Cause:** The token expired or the shell variable is gone.
    - **Fix:** Repeat section 7.

16. **`403` on an admin route**
    - **Cause:** The signed-in user is not an admin.
    - **Fix:** Use the bootstrap admin.

17. **A redirect on `/api/cranes`**
    - **Cause:** Missing trailing slash.
    - **Fix:** Use `/api/cranes/`.

18. **Port already allocated**
    - **Cause:** Another program uses the port.
    - **Fix:** Change `APP_PORT` (API) or `WEB_PORT` (web app), then run `up -d --force-recreate`.

19. **`ModuleNotFoundError: No module named 'fastapi'` (or `pytest`) when running `python -m pytest`**
    - **Cause:** The Python virtual environment is not active in this terminal (a new terminal starts without it).
    - **Fix:** Activate it:
      ```bash
      source .venv/Scripts/activate
      ```
      Or, if your folder is named `venv`:
      ```bash
      source venv/Scripts/activate
      ```
      The prompt then starts with `(.venv)` or `(venv)`. If needed:
      ```bash
      pip install -r requirements-dev.txt
      ```

20. **`verify_stack.sh` reports `web container is healthy` as FAIL right after a restart**
    - **Cause:** The container was still starting.
    - **Fix:** The script already waits up to 60 seconds. Run it again, or check `logs crane-web`.

21. **`verify_stack.sh` reports `API image contains exactly the versions in requirements.lock` as FAIL**
    - **Cause:** The image is older than the lock.
    - **Fix:**
      ```bash
      docker compose --env-file .env.docker build --no-cache crane-app
      docker compose --env-file .env.docker up -d --wait
      ```

22. **`failed to get console mode for stdout: The handle is invalid.`**
    - **Cause:** Harmless message from Docker in Git Bash when output is piped.
    - **Fix:** Ignore it; the scripts filter it out.

23. **`WARNING: The directory '/home/app/.cache/pip' ... is not writable`**
    - **Cause:** The `app` user has no home folder, so pip cannot keep a cache.
    - **Fix:** Ignore it, or add `--disable-pip-version-check`.

24. **`scan_security.sh` prints `[FINDINGS]`**
    - **Cause:** A new flaw was published, or a base image aged.
    - **Fix:** See `docs/PROJECT-PHASES/Phase-11.1-CONTAINER-SECURITY.md`, section 9.

25. **`git status --short` shows nothing for this folder, or one line `./`**
    - **Cause:** The folder was never committed (Git shows an untracked folder as one line).
    - **Fix:** See `docs/PROJECT-PHASES/Phase-11.2-DEPENDENCY-LOCKING.md`, section 12.

## 16. Appendix: PowerShell equivalents

If you use PowerShell instead of Git Bash, these replace sections 7 and 10. All `docker compose` commands are identical.

**Log in and capture a token:**

```powershell
$secure = Read-Host "Admin password" -AsSecureString
$plain = [System.Net.NetworkCredential]::new("", $secure).Password
$body = @{ email = "admin@example.com"; password = $plain } | ConvertTo-Json
$login = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8004/api/auth/login `
  -ContentType "application/json" -Body $body
$token = $login.access_token
$plain = $null
"token length: $($token.Length)"
```

**Call a protected endpoint:**

```powershell
$h = @{ Authorization = "Bearer $token" }
Invoke-RestMethod -Uri http://localhost:8004/api/lookups -Headers $h
```

**Run the tests** (Windows virtual environment):

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
```
