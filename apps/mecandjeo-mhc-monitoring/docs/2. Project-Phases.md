### How It Works

The model starts from a `User`, then connects role-specific profile tables for operator, manager, and admin details.

`Crane` stores the physical MHC asset. It has both a system code and an operator-facing `mhc_number`.

`Shift` represents the operator's login/operation session. It stores `operator_id`, `crane_id`, and `mhc_number` so the actual MHC used in the operation is captured directly.

`TaskLog` stores the actual crane work. `DelayLog` stores downtime against a task, including both standard delay categories and optional custom site-specific delay text.

`PerformanceSnapshot` is reserved for calculated metrics such as total task minutes, delay minutes, effective work minutes, container count, and moves per hour.

### Security Notes

- Passwords are represented only as `password_hash`; plain passwords should never be stored.
- RBAC roles are modeled as `operator`, `manager`, and `admin`.
- Audit logging exists in the schema so sensitive actions can later be traced.
- Standard delay values are stored as strings for flexibility, but admin-controlled reference data should be introduced before production.

- `bcrypt==4.0.1` is pinned because `passlib==1.7.4` is not compatible with `bcrypt==5.0.0`.
- Test secrets are at least 32 characters to avoid weak HMAC key warnings.

### How It Works

An operator logs in, receives a JWT, and uses that token to start a shift. The shift start request includes the selected MHC number and shift code. The API looks up the active crane by MHC number, validates the shift code as A, B, or C, and creates an active shift owned by the current operator.

The operator can then start one task, log delays against that task, end delays, end the task, record working conditions, and finally end the shift. A task cannot close while a delay is still active. A shift cannot close while a task is still active.

### How It Works

An admin logs in and sends a bearer token to the Phase 6 endpoints. The RBAC dependency verifies the `admin` role before any database action. User and crane records are retired with `is_active: false`, so past shifts, tasks, and reports continue to keep their original meaning.

Reference data stores a stable machine `code`, a human-friendly `label`, and an optional short key such as `AT` for awaiting trucks. The seed helper inserts the default values once and safely does nothing on later runs.

Every successful admin write creates an `audit_logs` record. The API also blocks an administrator from deactivating or demoting their own account, avoiding a simple administrative lockout.

### Security Notes

- Public registration can create operators only.
- Passwords created or reset by an admin are hashed with bcrypt.
- Duplicate user emails, crane identities, and reference category/code pairs are rejected.

### How It Works

1. When `AUTO_CREATE_SCHEMA=true` (local only), the API creates tables, then runs the bootstrap.
2. Bootstrap inserts any missing reference values (30 in total), inserts sample cranes only when `SEED_SAMPLE_DATA=true`, and creates the admin only when the email and password settings exist and no account with that email exists.
3. The bootstrap prints one line: `bootstrap: reference_data_added=N cranes_added=N admin_created=True|False`. Running it again prints zeros and `False`.
4. `GET /api/lookups` returns active reference values in four groups (`nature_of_work`, `working_area`, `delay_type`, `shift_code`) plus active cranes as `{id, mhc_number}`.
5. When an operator starts a task or delay, the submitted values are trimmed, lower-cased, and compared with active reference data. Unknown or retired values return `400`. `custom_delay_type` remains free text.

### Security Notes

- The bootstrap password is read from the environment, never from code, and is stored only as a bcrypt hash.
- A password shorter than 12 characters stops startup with an explicit error.
- Bootstrap never changes an existing account, so restarting cannot reset or take over an admin.
- Bootstrap creation is written to the audit log (`user.bootstrapped`).
- `/api/lookups` is read-only and requires a valid token. It exposes no user data and only active records.
- Sample cranes are controlled by `SEED_SAMPLE_DATA`, which must stay off outside local development.
- Missing tokens and invalid tokens both return `401` with the `WWW-Authenticate` header.
- `.env.docker` is ignored by Git. Real secrets must come from a secrets manager in cloud environments.

### How It Works

1. In development the browser talks only to `http://localhost:5173`. Vite forwards `/api` and `/health` to the backend on port 8004, so no CORS settings are needed.
2. After login the token is kept in `sessionStorage` and sent as a Bearer header. Any `401` on an authenticated call clears it and returns the user to the login page.
3. The operator screen reloads its state from `GET /api/operators/me/active`, so a page refresh never loses the open shift, task or delay.
4. "This shift" figures come from the per-shift summary and start at zero for every new shift; "All time" figures stay separate.
5. Times are sent and stored as naive UTC and shown in the viewer's local time.
6. Operators choose work types and areas from `GET /api/lookups`, which lists only active values. The API rejects anything else.
7. The manager overview refreshes itself every 15 seconds. Reports and the CSV download share the same filters.
8. The theme is applied to the page and remembered per user in that browser.

### Security Notes

- A wrong current password on change-password returns `400`, not `401`, so a typo does not sign the user out.
- New passwords follow the same policy as registration and admin resets (8 or more characters with a lowercase letter, an uppercase letter, a number and one of `! @ # % $`), checked in the browser first and again by the API.
- The change is written to the audit log as `user.password_changed`; no password is ever logged.
- Admins cannot deactivate or demote themselves; the UI also hides those controls.
- Role guards in the frontend are a convenience only. The backend remains the real authority and returns `403` for the wrong role.
- Locked reference-data codes cannot be edited because past records store them.
- `.env.docker` stays out of Git. The demo accounts share one documented password and are for local use only.
